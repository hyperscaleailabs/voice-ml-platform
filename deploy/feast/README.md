# deploy/feast/ — Feast repository

Feast is an adapter here, not the source of truth. The feature definitions live
in Python in `src/vmp/features/views.py`; this directory is generated from them.

```
src/vmp/features/views.py   ->   deploy/feast/features.py   ->   feast apply
     (the definition)              (generated, do not edit)        (the registry)
```

| File | What it is |
|---|---|
| `feature_store.yaml` | Feast config: `local` provider, Redis online store, file (Parquet) offline store. |
| `features.py` | Generated by `vmp features feast-export`. Entities and the three feature views. Regenerate, never hand-edit. |

## The three views

They mirror `views.py` exactly, including TTLs and dtypes.

| View | Entity (join key) | TTL | Source | Features |
|---|---|---|---|---|
| `session_features` | `session` (`session_id`) | 1 h | stage traces | `turn_count`, `avg_user_utterance_s`, `avg_response_ms`, `last_intent`, `accent_profile` |
| `speaker_features` | `speaker` (`speaker_id`) | 7 d | evaluation runs | `wer_7d`, `exact_match_rate_7d`, `wake_word_corrections_7d` |
| `device_features` | `device` (`device_id`) | 1 d | edge devices | `edge_bundle_version`, `p95_ttfa_ms_24h` |

Short TTLs are the point of the session view: a feature older than an hour
describes a conversation that has ended, and serving a stale `avg_response_ms`
into a routing decision is worse than serving nothing.

## Generating this repository

`features.py` is emitted by `vmp.features.feast_export.feast_source`, which walks
the in-code view registry and writes Feast declarations. Generating it imports
no Feast; only `feast apply` does.

```bash
# regenerate into this directory
vmp features feast-export --out deploy/feast --project vmp --data-root data

# see what would be written, write nothing
vmp features feast-export --dry-run
```

The command writes `<out>/feature_repo/features.py`; the copy checked in here
sits at `deploy/feast/features.py`. After regenerating, apply it:

```bash
cd deploy/feast && feast apply
```

Adding a feature is therefore a three-step change: edit `views.py`, regenerate,
`feast apply`. A pull request that changes `views.py` without a regenerated
`features.py` is out of sync, and the offline Parquet schema will not match what
Feast expects to read.

## Materialize schedule

Materialization moves rows from the offline Parquet store into Redis so serving
reads are a single online lookup.

**In the cluster** it is a CronJob, already defined at
`deploy/k8s/base/feast-materialize-cronjob.yaml` — every 15 minutes,
`concurrencyPolicy: Forbid`, `backoffLimit: 2`, a 900 s deadline. Do not add a
second scheduler here; change the schedule in that file.

The cadence is chosen per view rather than per store:

| View | Freshness needed | Effective cadence |
|---|---|---|
| `session_features` | seconds — an in-flight conversation | the stream updater writes online directly; the CronJob only backfills |
| `speaker_features` | hours — recomputed when an eval run finishes | the 15-minute CronJob |
| `device_features` | hours — devices report on their own schedule | the 15-minute CronJob |

**By hand**, for one view and one window:

```bash
vmp features materialize --view speaker_features \
  --offline-root "$VMP_FEATURE_STORE_ROOT" \
  --redis-url redis://redis:6379/1 \
  --start 1757000000 --end 1757086400

# validate the plan without writing
vmp features materialize --view speaker_features --dry-run
```

Without `--redis-url` the online store is in-memory, which is what the tests and
`examples/demo_features.py` use.

## Point-in-time correctness

Training data is joined from the offline store with a point-in-time join: for
each training row, the feature values as of that row's `event_ts`, never later.
This is why every view carries `event_ts` and why the offline store keeps history
instead of overwriting. Serving reads the online store, which holds only the
latest row per entity within the TTL. The same view definition drives both, so a
feature cannot mean one thing in training and another in serving.
